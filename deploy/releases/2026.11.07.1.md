# 2026.11.07.1 更新说明与 Linux 升级指南

发布日期：2026-11-07。此编号是 KaneoB 定制版本号，侧边栏中的上游版本号仍可能显示 `v2.48.0`。

## 本次更新

| 功能 | 使用方式与影响 |
| --- | --- |
| 主负责人 + 协作人 | 项目任务保留一名主负责人，最多添加 50 名协作人；“我的任务”显示“我负责 / 我协作”，任务总数不重复计算，按人统计仍归主负责人 |
| 成员分配权限 | 默认 member 角色可以分配任务负责人及协作人；候选人仍受当前项目访问范围限制，管理员可以在角色设置中关闭分配权限 |
| 展开、收起与列宽 | 项目任务的列表和层级视图支持全部展开/全部收起；拖动列边界或使用方向键调整宽度，双击恢复单列宽度，也可恢复全部默认宽度 |
| 父任务 | 新建任务及任务属性中可选择、替换、清除同项目父任务，阻止自关联和循环；历史关系保留 |
| 子任务负责人 | 新建子任务默认继承父任务主负责人，显式选择的负责人优先；后续修改父任务负责人不会自动覆盖已有子任务 |
| 需求 Excel 附件 | 创建需求时上传 `.xlsx` / `.xls`，单个不超过 10 MiB，每个需求最多 20 个；保存后可下载或按编辑权限移除，文件作为附件保存，不解析为需求记录 |
| 首页 Portal | 公共入口与个人入口，支持名称、HTTP/HTTPS 地址、图标、颜色、说明、分组、搜索和拖动排序；公共入口由所有者或具备管理设置权限的管理员维护，个人入口仅本人可见 |
| 更新记录与提示 | 首页首次提示当前账号未读版本，可从侧边栏“更新记录”查看历史；点击“知道了”或打开历史记录后，将已读状态保存到数据库 |

列宽按账号、项目和视图保存在当前浏览器。Portal 配置、协作人和更新已读状态保存在数据库，随数据库备份恢复。

## 数据库与部署变化

应用启动时自动执行迁移 [`0078_complete_shotgun.sql`](../../apps/api/drizzle/0078_complete_shotgun.sql)：

- 新增 `portal_link`、`release_read`、`requirement_attachment` 三张表。
- 为 `task` 新增 `collaborator_ids` 字段和索引，并添加协作人去重、离开工作区或删除用户时的清理触发器。
- 为现有 `workspace_role.role = 'member'` 一次性补充 `task:assign`；保留其他权限配置，升级后管理员仍可修改。其他自定义角色不自动增加权限。
- 保留原有任务、项目、需求、成员、灵感、报表快照及历史父子关系。

本次不需要新增环境变量或额外服务，继续使用原有 PostgreSQL 16、Compose 和持久化目录。不要重新生成数据库密码或 `AUTH_SECRET`。

Excel 附件的二进制数据存储在 PostgreSQL 中，现有完整 `pg_dump` 备份可以覆盖这些附件。未保存需求的草稿附件在 24 小时后由定时任务清理。描述、评论和灵感的通用附件仍使用原 S3 兼容存储，已有 S3 对象仍需按原方案单独备份。

## Linux 服务器升级

本次使用仓库源码构建镜像，镜像标签采用 Git 提交号。先在服务器确认源码目录、实际部署目录、Compose 项目名及数据盘挂载位置；下文默认采用 [README 的 Linux 运维布局](../../README.md#linux自动备份异地同步和受保护升级)：

```text
/opt/kaneoB/                 源码
/opt/kaneob-ops/main.py      已安装的运维工具
/etc/kaneob/ops.json         现有私有运维配置
/data/kaneob/               现有部署与数据，包含 .env、compose.yml、postgres 等
```

下列命令在 Bash 的 root shell 中执行，适用于已经配置本仓库 Linux 运维工具、加密公钥和异地同步的服务器。自定义路径时同时替换命令参数。

### 1. 拉取代码并构建，现有服务继续运行

```bash
set -eu
cd /opt/kaneoB

# 有本地修改或不在 main 时停止，先处理差异。
test "$(git branch --show-current)" = main
test -z "$(git status --porcelain)"
git pull --ff-only origin main

version=$(git rev-parse --short=12 HEAD)
image="kaneob:$version"
docker build -f Dockerfile.kaneo -t "$image" .

docker compose -p kaneob-linux --env-file /data/kaneob/.env \
  -f /data/kaneob/compose.yml config --quiet
docker compose -p kaneob-linux --env-file /data/kaneob/.env \
  -f /data/kaneob/compose.yml ps
```

需要固定到本次版本时，使用本次 GitHub 提交页的完整 SHA，在服务器另建源码检出目录构建该提交，避免覆盖已有工作区修改。不要用上游 `ghcr.io/usekaneo/kaneo:latest` 替代此处构建的定制镜像。

### 2. 执行带强制备份的升级

```bash
# 沿用上一段的 image 变量；在新 shell 中执行时从当前源码提交重新计算。
cd /opt/kaneoB
image="kaneob:$(git rev-parse --short=12 HEAD)"
python3 /opt/kaneob-ops/main.py --config /etc/kaneob/ops.json upgrade "$image"
```

升级工具将执行以下步骤：

1. 检查现有数据挂载、数据库、服务健康和运维配置。
2. 将 gateway 置为维护状态，停止旧应用写入，数据库容器保留。
3. 生成完整数据库备份，在隔离的 PostgreSQL 16 中实际恢复并核对记录，然后加密、异地同步并校验；本地构建的旧镜像同时留档。
4. 只有上述步骤成功才切换新镜像、启动应用并自动执行迁移。
5. 健康检查和关键业务表记录核对通过后重新开放入口，并记录升级前备份位置。

备份、恢复校验或异地同步失败时，新镜像不会启动，工具尝试恢复旧应用。若新版本可能已执行迁移但启动或验收失败，工具保持维护状态并停止应用，保留 `state/recovery-required.json`，供按备份恢复。

本次升级有短暂维护窗口。继续使用原有 `.env`、Compose 项目名和持久化目录；不要执行 `docker compose down -v`、重新初始化部署或删除数据目录。

**如果现有服务器只有普通 Compose、尚未配置这套运维工具，不要对已有数据运行 `init`，也不要直接套用上面的 `upgrade` 命令。** 先保留原部署配置并完成一次人工备份、独立恢复验证和异地保存，再按实际 Compose 服务、端口和挂载制定切换步骤。不能把数据目录或命名卷改成一个新的空位置。完整保障范围和首次配置见 [README](../../README.md#linux自动备份异地同步和受保护升级)。

### 3. 升级后验收

```bash
docker compose -p kaneob-linux --env-file /data/kaneob/.env \
  -f /data/kaneob/compose.yml ps
curl --fail --silent --show-error http://127.0.0.1:5173/api/health

# 使用当前部署配置检查并记录运维版本状态。
python3 -m json.tool /data/kaneob/state/release.json
systemctl list-timers kaneob-backup.timer
```

如果 gateway 使用自定义端口，替换健康检查地址。刷新网页后确认：

- 原有项目、需求和任务数量正常，附件和历史记录仍能打开。
- 首页显示 Portal 和首次更新提示，侧边栏可以查看“更新记录”。
- 项目列表/层级可以全部展开和收起，调整列宽后刷新能保留。
- 任务属性可设置主负责人、协作人及父任务；普通成员能在项目允许范围内分配任务。
- 新建子任务带出父任务负责人；新建需求上传 Excel 后，详情中可以下载同一附件。

## 升级失败时恢复

先查看 `/data/kaneob/state/recovery-required.json` 中记录的阶段和 `backup` 路径，保留原数据库和维护状态。若迁移可能已经执行，不要只把镜像改回旧版后直接启动。

从异地取回对应加密数据归档、同名 `.sha256`，以及需要的 `images/` 镜像归档。以下示例的备份文件名需要替换为状态文件中的实际文件，恢复私钥仅放在受保护的恢复环境：

```bash
backup=/data/kaneob/backups/kaneob-实际文件名.tar.age
export TMPDIR=/data/kaneob/backups

python3 /opt/kaneob-ops/main.py --config /etc/kaneob/ops.json verify \
  "$backup" --identity /secure/kaneob-recovery.agekey

# 使用新的空目录、项目名和端口，原实例数据保留。
python3 /opt/kaneob-ops/main.py --config /etc/kaneob/ops.json restore \
  "$backup" --identity /secure/kaneob-recovery.agekey \
  --target-root /data/kaneob-restored-20261107 \
  --project kaneob-restored-20261107 --port 15173
```

`restore` 成功后仅启动数据库。先核对恢复实例的配置、数据和外部集成，确认旧实例停止写入，再按 [README 的正式接管步骤](../../README.md#5-验证灾难恢复与回退)安装恢复配置并执行 `activate`，最后切换反向代理。使用外部 S3 对象的备份需要 `--database-only`、新桶及额外的对象恢复步骤，详见 [附件恢复说明](../../README.md#6-启用附件后的备份和恢复)。恢复点之后的新写入不包含在旧备份中。
